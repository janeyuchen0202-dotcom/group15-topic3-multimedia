Geometric Image Transformations

Geometric transformations move pixels without changing their values. This page shows how one 3 × 3 matrix describes translation, rotation, scaling, affine and perspective warps, and how the output image is actually filled in.

Overview

Coordinates, not colours. A geometric transformation maps a position (x, y) to a new position (x′, y′); the pixel values stay the same and only their places change. Writing points in homogeneous coordinates (x, y, 1) lets every transformation on this page be a 3 × 3 matrix. Two transformations in a row then become one matrix product, and the order matters: rotating and then translating differs from translating and then rotating.

A hierarchy of transformations. Each step up adds freedom and gives up a guarantee (Szeliski, 2011, Table 2.1; Hartley & Zisserman, 2004).

  • Translation shifts the image (2 degrees of freedom).
  • Rigid adds rotation (3) and keeps lengths.
  • Similarity adds uniform scaling (4) and keeps angles.
  • Affine adds shear and unequal scaling (6); parallel lines stay parallel.
  • Projective, also called a homography (8), uses the matrix’s last row as well. Only straight lines are guaranteed to stay straight, which is exactly what happens when a flat page is photographed at an angle.

Finding the matrix. Each matching pair of points gives two equations, so an affine transform needs three pairs and a homography four, with no three of them on one line (OpenCV’s getAffineTransform and getPerspectiveTransform). Automatic feature matches contain mistakes, so systems fit many pairs with RANSAC (Fischler & Bolles, 1981), which copes with a significant share of gross errors.

Filling the output. The obvious method, forward mapping, pushes each source pixel to its new place. Because targets are rarely whole numbers, it leaves holes and overlaps. Practical systems use inverse mapping instead: for every output pixel, compute where it came from with the inverse matrix and interpolate the source at that point (Szeliski, 2011, §3.6). OpenCV’s warpAffine and warpPerspective work this way. Every warp therefore relies on the kernels in Image Resizing and Interpolation, and output pixels that map outside the source need a border rule, such as a constant colour.

Cost. Each output pixel needs one small matrix product and one interpolation, so the cost grows with output size and kernel width. Every resampling also blurs a little, so it is better to multiply the matrices first and resample once, an idea that returns in Efficient Multimedia Processing.

Applications

Document scanning

Dropbox’s scanner looks for the page as a convex quadrilateral, because a rectangular page photographed at an angle projects to one, then fits it to a rectangular shape: a perspective warp defined by four corners. Google’s ML Kit document scanner offers a similar flow on Android, with edge detection, cropping and automatic rotation running on the device.

Sources: Xiong (2016), Dropbox Tech Blog; Google, ML Kit document scanner documentation.

Panorama stitching

Brown and Lowe (2007) stitch photos automatically: they match invariant local features, use RANSAC to reject wrong matches, estimate a 3 × 3 homography for each image, and blend the warped images with multi-band blending.

Source: Brown & Lowe (2007).

Medical image registration

elastix aligns medical scans from different modalities (for example MR and CT), from different time points or from different subjects, using rigid and nonrigid transformations that users configure and compare.

Sources: Klein et al. (2010); elastix.dev.

Learning reflection

I expected this section to be about formulas, but the real lesson was about direction. Mapping source pixels forward felt natural, yet it leaves holes; asking “where did this output pixel come from?” fixes that and explains why every rotation in an image editor needs interpolation. Building the comparison table also made the hierarchy click: each extra degree of freedom buys flexibility but gives up a guarantee, from lengths to angles to parallel lines. The Dropbox case showed me that the hardest part in practice is finding the four corners, not applying the matrix. I still want to understand how RANSAC decides how many random samples to try.

Key learning points

  • Homogeneous coordinates make every transformation here a 3 × 3 matrix, so chains of transformations combine by multiplication.
  • Degrees of freedom decide how many point pairs are needed: three for affine, four for a homography.
  • Inverse mapping plus interpolation avoids holes; a border rule handles pixels that fall outside the source.

Misconception

“Applying the transformation to every source pixel is enough.” Forward mapping leaves holes and overlaps because targets are rarely integers. Practical code maps each output pixel backwards and interpolates (Szeliski, 2011, §3.6).

Verified claim

OpenCV’s warpPerspective computes dst(x, y) = src((M11x + M12y + M13) / (M31x + M32y + M33), (M21x + M22y + M23) / (M31x + M32y + M33)) when the flag WARP_INVERSE_MAP is set; otherwise the matrix is first inverted and then used in this formula. In other words, OpenCV samples the source once for every destination pixel.

Checked in the OpenCV 4.x documentation of cv::warpPerspective (Geometric Image Transformations module).
