Efficient Multimedia Processing

A 4K video frame has over eight million pixels and often has to be processed in a few tens of milliseconds. This page explains where processing time goes and which choices reduce it: algorithm, resolution, memory access and hardware.

Overview

Count the work. Most image operations repeat the same calculation for every output pixel, so the cost is roughly pixels × operations per pixel, plus the bytes that must be moved. Resolution sets the scale: a 3840 × 2160 frame has 8.3 million pixels, four times a 1080p frame. At 30 frames per second, the whole pipeline has about 33 ms per frame.

Choose a cheaper algorithm. The same result can often be computed with less work. A separable K × K filter, such as a box or Gaussian blur, runs as a horizontal pass and then a vertical one: 2K instead of K² operations per pixel (Szeliski, 2011, §3.2). For large kernels the FFT is cheaper still, and SciPy’s documentation calls FFT convolution generally much faster for large arrays (see Frequency-Domain Transformations). An integral image is built in one pass, after which any rectangle sum needs only four array references, one reason Viola and Jones (2004) could detect faces in real time. Choosing a kernel in Image Resizing and Interpolation is the same kind of quality-for-speed decision.

Work at the resolution you need. Halving width and height leaves a quarter of the pixels. Image pyramids store an image at several sample densities, so coarse searches can run on the small levels (Burt & Adelson, 1983). Google’s HDR+ camera shows a 1.6-megapixel viewfinder at 15–30 frames per second and runs its expensive full-resolution merge only after the shutter is pressed (Hasinoff et al., 2016).

Keep data close. Moving data often costs more than arithmetic. The Roofline model bounds attainable performance by the smaller of peak compute and memory bandwidth × operational intensity, the number of operations per byte of DRAM traffic (Williams, Waterman & Patterson, 2009). Simple per-pixel stages do few operations per byte, so they often hit the bandwidth limit. The remedy is locality: process tiles that fit in cache and fuse stages so that intermediate images never travel to main memory. Halide separates an algorithm from this schedule; its authors report that naive and optimised versions of a pipeline often differ by an order of magnitude (Ragan-Kelley et al., 2013).

CPU, GPU or fixed hardware. A CPU runs a limited number of threads at once, while a GPU keeps thousands of lightweight threads in flight and suits uniform per-pixel work, such as the warps in Geometric Image Transformations. Copies between them are slow: NVIDIA’s guide contrasts 898 GB/s of GPU memory bandwidth on a V100 with 16 GB/s over PCIe, and advises keeping intermediate data on the GPU. Video decoding and encoding can run on dedicated NVDEC and NVENC units, and FFmpeg can keep the frames in GPU memory between them.

Applications

HDR+ burst photography

Google’s HDR+ merges a burst of raw frames on the phone. While the camera app is open, a low-resolution viewfinder pipeline (1.6 MP at 15–30 frames per second) runs; after the shutter is pressed, a full pipeline written in Halide produces a 12-megapixel photo in about 4 seconds on the device.

Source: Hasinoff et al. (2016).

GPU transcoding with FFmpeg

NVIDIA’s guide runs FFmpeg with -hwaccel cuda -hwaccel_output_format cuda so decoded frames stay in GPU memory, resizes them with the decoder’s built-in resizer or scale_cuda, and encodes them with h264_nvenc, hevc_nvenc or av1_nvenc.

Source: NVIDIA, “Using FFmpeg with NVIDIA GPU Hardware Acceleration”.

Real-time face detection

Viola and Jones made detection fast with an integral image, computed in one pass so that any rectangle sum needs four array references, and with a cascade that discards background regions early.

Source: Viola & Jones (2004).

Learning reflection

Before this section I assumed speed was mostly about faster hardware. Building the trade-off table showed me that the biggest wins usually come earlier: choosing a separable filter, working at a lower resolution or avoiding a copy. The Roofline model changed how I read benchmark numbers, because a stage that does little arithmetic per byte cannot get faster just by adding cores. The HDR+ paper was the most useful case, since it shows a team using a small viewfinder pipeline and a slower full-resolution path for different needs. I still find GPU memory rules such as coalescing abstract, and I would like to measure them in a small experiment.

Key learning points

  • Cost ≈ pixels × operations per pixel + bytes moved, and resolution multiplies everything.
  • Algorithm choice (separable filters, the FFT, integral images) can cut work by large factors before any hardware changes.
  • Data movement is a first-class cost: fuse stages, tile for caches and keep frames on the GPU.

Misconception

“Moving work to the GPU always makes it faster.” Transfers over PCIe are far slower than GPU memory, and NVIDIA advises minimising them even if some kernels then run on the GPU with no speed-up.

Verified claim

“The peak theoretical bandwidth between the device memory and the GPU is much higher (898 GB/s on the NVIDIA Tesla V100, for example) than the peak theoretical bandwidth between host memory and device memory (16 GB/s on the PCIe x16 Gen3).”

Quoted from NVIDIA’s CUDA C++ Best Practices Guide, §10.1 “Data Transfer Between Host and Device” (online version 13.5, checked 25 Nov 2026).
